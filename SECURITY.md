# Security Policy

## Why this matters more than usual

`repo-kit` is a flake-parts module that other repositories import. It runs **inside their
flake evaluation** and **writes files they commit**: their `.envrc`, devcontainer and Dependabot
config, and (through `init`) a new repository's CI caller. A defect here does not stay here. It lands in every repository that
bumps its lock.

Treat anything in these categories as a security issue, not a bug:

- A generated file that runs code a consumer did not ask for (an `.envrc` that sources
  something unexpected, a devcontainer command, a workflow step).
- A generated Dependabot or CI config that weakens a consumer's supply-chain controls
  (drops the cooldown, unpins an action, widens permissions).
- Anything that reads or writes outside the consumer's own source tree, or reaches the
  network during evaluation.
- A pinned input (`files`, `treefmt-nix`, `flake-parts`, `nixpkgs`) that resolves to
  something other than its reviewed revision.

## Supported versions

Only **`main`** is supported. Consumers pin it through their `flake.lock`, so there is no
release branch to backport to. A fix ships as a new commit on `main`, and a consumer gets it
with a lock bump.

## Reporting a vulnerability

**Do not open a public issue.**

Use GitHub's private reporting:
**[Report a vulnerability](https://github.com/ismailkattakath/repo-kit/security/advisories/new)**

If that is unavailable to you, email **ismail@kattakath.com** with `SECURITY` in the
subject.

Please include:

- The repo-kit commit (from the consumer's `flake.lock`) and the option settings involved.
- The generated file or check that misbehaves, and what it does.
- What an attacker gains — be concrete about impact.
- Minimal reproduction steps. A small flake that triggers it is worth more than prose.

### What to expect

| Stage | Target |
|---|---|
| Acknowledgement | within **72 hours** |
| Initial assessment | within **7 days** |
| Fix published, or a stated timeline | within **30 days** |

This is a small project maintained in spare time — those are honest targets, not a
contractual SLA. If a deadline slips you will be told, not ignored.

You will be credited in the advisory unless you ask not to be. Please give us a chance to
publish a fix before disclosing publicly.

## Out of scope

- Vulnerabilities in **upstream inputs** themselves (nixpkgs, flake-parts, treefmt-nix,
  mightyiam/files) — report those upstream. A repo-kit pin to a known-bad revision is in scope.
- Vulnerabilities in **consumer repositories'** own code.
- Reports generated by a scanner with no demonstrated impact on this code.
